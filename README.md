把一次组会要讲的东西，做成一份**能站起来讲、经得起追问**的 `.pptx`。覆盖三种汇报——论文阅读、实验报告、项目进展——一份 PPT 里可以只讲一类，也可以三类混排、自动分区。

**30 秒看到成品**（前提：已装 Python 与 `python-pptx`；没装先看 [快速安装](#快速安装)）：

```text
cd ~/.你的vibe coding工具/skills/grad-seminar-deck
pip install python-pptx pillow numpy lxml
python scripts/build_deck.py assets/deck.example.json -o 样例.pptx
```

翻一遍这份 27 页的样例，就知道三类汇报各长什么样；再照着自己的内容改 `deck.json`。只想先跑通最小例子，直接跳到[快速开始](#快速开始)。

> **AI 负责排版，你负责讲话。** 它能把你要讲的东西排成一页一页，但「这篇论文到底主张什么」「哪个实验印证了哪条观点」「这对我的课题意味着什么」——这三件事它不替你想。内容点填不出来时，它只会告诉你缺哪一条，不会拿套话糊过去。
>
> 它也不帮你把别人的工作说成自己的。原文没有的图，它不会画一张顶替；等级查不到，它要求你写「未核实」而不是猜一个期刊等级。风格上它同样克制：统一的白底、单一强调色、无渐变无阴影——**风格统一比单页好看更重要**。

### 为什么要检查点，不要一键生成？

一键生成的 PPT 通常不会崩在「没生成出来」，而是崩在四个地方，这四处恰好是机器能查、人却常常懒得查的：

1. **结构跑偏**——讲成论文复述，缺「实验怎么印证观点」和「对我有什么启发」。这两块正是导师必问的，也最容易漏。所以内容点不是建议，是检查脚本逐条核对的清单：9 个内容点缺一个就 `[FAIL]`，退出码非 0，不让它带病进下一步。
2. **证据残缺**——满页文字没有原文图表，或者截了图但表头被切、坐标轴断开。所以裁图不是「按框裁完就完」，而是裁完立刻判定**四条边有没有墨迹跨过边界**，跨了就给建议坐标；最后拼一张审片图，被切的那张直接红框标 `EDGE`。
3. **页数失控**——某篇论文讲着讲着变成 6 页，整场超时。所以每单元 2–4 页是硬约束，越界直接报错退出（退出码 5），没有「悄悄多两页」这个选项。
4. **交付不检查**——字太小、图注压在图上、文字压到底部结论条，投到屏幕上才发现。所以生成后还有一道静态体检：溢出、字号、遮挡、越界、dpi、空页，零 `FAIL` 才算过。

代价是流程变长：写内容 → 查讲全没有 → 生成 → 查版面 → 逐页看图 → 交付。换来的是**每次交付前都知道自己漏了什么**，而不是等被问到才发现。

> **边界要说清**：这套检查能确认「页面里没有文字溢出」「这张图没被裁断」「9 个内容点都登记了」，但它**不能**确认「这个数字是对的」「这条结论方向没反」「这一页讲得动人」。前三关可以自动化，第四关（事实关）只能人对着原文核。一个编得很圆的故事，能顺利通过前三关。

## 结构与流水线

**👉 [references/](references/)** —— 三类汇报的逐页内容清单、`deck.json` 全字段、截图表判据、四关自检清单，各自独立成篇。

流水线是五个带检查点的步骤，任何一步不过就不往下走：

```text
deck.json ──► check_structure.py ──► build_deck.py ──► check_deck.py ──► render_deck.ps1 ──► 人眼
             「讲全了没有」          「生成 pptx」      「版面硬伤」       「逐页 PNG」      「四关之 3、4」
               内容点/页数/证据        自动分区与页码      溢出/字号/遮挡      PowerPoint 导出    遮挡·图注·别扭
```

设计上有条硬规矩：**内容与样式分离**。你只写 `deck.json`（讲什么），版式、字号、分区、页码、页脚全部由 `build_deck.py` 决定（怎么排）。所以改内容永远不用碰样式，也不会出现「第 5 页字突然变小了」这种事。

## 快速安装

**前置条件**

- Python 3，以及四个库：`python-pptx`（生成 pptx）、`pillow`（读图算尺寸与 dpi）、`numpy`（裁图边界检测）、`lxml`（`python-pptx` 的依赖）
- *可选：* 本机 PowerPoint。只有最后一步「导出 PNG 逐页目检」需要它；没有也能生成 PPT，只是目检要你手动打开逐页看
- *可选：* 中文字体。Windows 用微软雅黑，macOS 会自动找 PingFang SC；Linux 需要 Noto Sans CJK 或文泉驿

**装依赖**

```bash
pip install python-pptx pillow numpy lxml
```

→ **效果**：装上生成 pptx、处理图片、算版面所需的四个库；已装过会显示 `Requirement already satisfied`，不会重复装。

**验证环境**

```bash
python -c "import pptx, PIL, numpy, lxml; print('依赖齐了')"
```

→ **效果**：四个库都能导入就打印「依赖齐了」；报 `ModuleNotFoundError` 说明缺库，先补装再往下走。

**验证跑通**（就是开头那三条命令）

```bash
cd ~/.你的vibe coding工具/skills/grad-seminar-deck
python scripts/build_deck.py assets/deck.example.json -o 样例.pptx
```

→ **效果**：生成一份 27 页的完整示范 PPT（2 篇论文 + 2 组实验 + 2 个项目），六种版式各有可对照的写法，直接对照着改成自己的内容最快。

**装在哪**：`~/.你的vibe coding工具/skills/grad-seminar-deck/`。这是用户级技能目录，所有项目都能用，不用每个项目装一遍。

## 速度与页数预算

**实测数据**（27 页样例，本机 Windows + 已装 PowerPoint，单次运行）：

| 环节                 | 耗时  | 说明                                           |
| -------------------- | ----- | ---------------------------------------------- |
| `check_structure.py` | 0.3 s | 纯静态解析，几乎不耗时，可以随手多跑           |
| `build_deck.py`      | 1.1 s | 27 页全部生成完毕                              |
| `check_deck.py`      | 1.1 s | 逐页逐形状量文字高度                           |
| `render_deck.ps1`    | 5.8 s | 27 页导出 PNG，约 0.2 s/页；冷启动第一次会慢些 |

**页数预算**：每个单元 2–4 页，这是硬约束。样例的 27 页 = 21 页内容 + 6 页自动生成（封面 1 + 目录 1 + 分区页 3 + 结束页 1）。反推一下就知道一场组会能讲多少：

| 你要讲                         | 内容页 | 加自动页后 | 大概时长   |
| ------------------------------ | ------ | ---------- | ---------- |
| 1 篇论文（精简 2 页）          | 2      | 6          | 5–8 分钟   |
| 1 篇论文（完整 4 页）          | 4      | 8          | 10–12 分钟 |
| 2 篇论文 + 2 组实验 + 2 个项目 | 21     | 27         | 25–30 分钟 |

> 上表前三列是算出来的，最后一列是**按每页 40–70 秒估的**，不是实测——讲多快因人而异。

> 讲不完是常态。**页数由内容决定，不由图决定**——一页塞两张图必然压字，宁可按 4 页讲。

## 功能速览

- **三类汇报，各自成章** —— 论文阅读汇报 / 实验报告 / 项目进展汇报；一份 PPT 可只含一类，也可三类混排。
- **每篇论文、每组实验、每个项目 2–4 页** —— 硬约束，越界直接报错退出（退出码 5），不会悄悄变成 6 页。
- **按种类自动分区** —— 自动插封面、目录、种类分区页（`01/02/03`）、每页角标（`论文阅读汇报 · 2/3`）、页码与页脚。
- **多篇论文自动要汇总表** —— 论文类多篇时，检查脚本会要求一页文献汇总表，列固定为「标题 / 出处 / 发布时间 / 一句话核心内容」，**行数必须等于篇数**。
- **从原文截图表做证据** —— 整页渲染 → `--propose` 给候选框 → `--bbox` 裁切 → **四条边墨迹跨界检测** → `contact_sheet.py` 拼审片图复审。
- **自动排版，字号自适应** —— 16:9、白底、单一强调色；正文按可用高度在 14–22pt 之间自动选，表格塞不下自动降字号（降到 12pt 仍不行就报警）。
- **三道自动检查 + 两道人工把关** —— 自动：内容完整性、版面硬伤、生成时预警（偏密 / 孤字 / 过稀）；人工：渲染成图逐页看、数字与出处回原文核对。
- **已知坑自动预警** —— 文字溢出、孤字（末行只剩一两个字）、表格过密、内容过稀（一页占不到半版）、插图 dpi 不足，全部在生成时就打出来，不用等投屏才发现。
- **版式只有六种，不给自由发挥** —— `bullets` / `image` / `table` / `cards` / `columns` / `statement`。不给「自由画布」是刻意的：一旦允许逐页调，二十页之后风格必然散掉。
- **`takeaway` 强制你写「所以呢」** —— 每页可写一句 45 字以内的结论条，压在页脚上方。写不出来，说明这一页还没想清。
- **`source` 落在页脚** —— 写 `原文 p.5 Table 1` 这种可回溯的出处，被追问时能直接翻回去。

**它不做的事**：不改你已有的 PPT（那用 `pptx`）；不写论文、不投稿、不审稿；不替你编数据——原文没有的图，它只会要求你写清「图片不可得」，不许自己画一张冒充。

### 什么时候用，什么时候别用

**用**：

```text
「做一份组会汇报 PPT」                      → 按你给的材料自动判断讲哪几类
「下周 journal club 轮到我」                 → 论文阅读汇报，每篇 2–4 页
「这周的实验做个报告」                       → 实验报告，每组 2–4 页
「基金中期检查要过一遍进度」                  → 项目进展汇报（科研项目）
「老师那个横向项目我要报一下进展」             → 项目进展汇报（委托项目，自动提示脱敏）
「/grad-seminar-deck」                      → 显式触发
```

**别用**：只要一篇论文的精读笔记（写 Markdown 更快）；只想改已有 PPT 的某一页（用 `pptx`）；写论文或审稿（不是这个技能的事）。

## 配合使用的技能

组会 PPT 只是链条中间的一环，前后各有搭子：

```text
	pdf-tool          ──►  本技能  ──►            pptx-tool
（PDF 逐页渲染成 PNG）         （从零生成）     （改已有 PPT 的某一页）
```

- **前面接 `pdf-tool`** —— 截图表前先把 PDF 逐页渲染成 PNG（`page-0001.png`…），这是裁图的底图。命令见[脚本与命令明细](#脚本与命令明细)末尾。
- **后面接 `pptx-tool`** —— 成品生成后如果要在 PowerPoint 里手改某一页、或者要基于别人的旧 PPT 改，用那个技能；本技能假定从零生成。
- **不要在两边来回改** —— 手改会被下次重新生成覆盖，原因见[六个实用技巧](#六个实用技巧)第 6 条。

## 用法

### 快速开始

最省事的方式是**说一句话**，剩下的（写 `deck.json`、跑三条命令、导出图给你看）由 AI 完成：

```text
你：做一份组会汇报 PPT，讲这两篇论文          → 论文阅读汇报，每篇 2–4 页
你：这周的实验做个报告，两组                  → 实验报告，每组 2–4 页
你：老师那个横向项目我要报一下进展             → 项目进展汇报（委托项目）
你：基金中期检查要过一遍进度，顺便讲一篇论文    → 两类混排，自动插两个分区页
```

做完你会拿到四样东西：`deck.json`（内容源文件）、`.pptx`（成品）、渲染出的逐页 PNG（供你目检）、以及一份体检结论（哪几页有问题、什么问题）。

### 手动跑（不想让 AI 代劳时）

按顺序走完下面几条命令即可。先建工作目录，把截好的图放进 `figs/`：

```bash
mkdir -p ~/deck_demo/figs
```

→ **效果**：建出 `deck_demo/` 及子目录 `figs/`，图片放 `figs/`，deck.json 和产物放 `deck_demo/` 根下——中间产物集中一处，下周改的时候不用到处找。

第一次练手可以先用任意一张 PNG 占位（命名成 `figs/f1.png`），跑通流程再换真图——不要把「还没截图」当成不能开工的理由。

然后写 `~/deck_demo/deck.json`（一份可直接跑的最小版本，见[数据格式](#数据格式deckjson)），接着：

```bash
cd ~/deck_demo
SKILL=~/.你的vibe coding工具/skills/grad-seminar-deck
```

→ **效果**：进入工作目录；`SKILL` 记下技能所在位置，后面命令直接复用，不用每次打一长串路径（换新终端要重新设一次）。

```bash
python "$SKILL/scripts/check_structure.py" deck.json
```

→ **效果**：检查「讲全了没有」——9 个内容点齐不齐、页数是否在 2–4 页、有没有证据图。打印每个单元一行 `[OK]`；有问题打 `[FAIL]` 并指出缺哪个内容点，退出码非 0。

```bash
python "$SKILL/scripts/build_deck.py" deck.json -o 组会汇报.pptx
```

→ **效果**：生成 `组会汇报.pptx`，自动补封面、目录、分区页、页码、页脚；顺带报出「偏密 / 孤字 / 内容过稀」这类提醒。

```bash
python "$SKILL/scripts/check_deck.py" 组会汇报.pptx
```

→ **效果**：静态体检——文字有没有溢出边框、字号是不是太小、元素有没有跑出页面、图被文字压没压住、插图 dpi 够不够、有没有空页。最后一行给「结论：通过」或列出需修的页号。

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File "$SKILL/scripts/render_deck.ps1" -Pptx "组会汇报.pptx"
```

→ **效果**：调用本机 PowerPoint 逐页导出 PNG 到 `render/`，每页一张；没有 PowerPoint 会明确报错，而不是静默跳过。

然后**逐张看**：有没有字被压住、图注是否完整、字够不够大、有没有半页空白。机器查不出「不好看」，这一步不能省。

### 每类汇报怎么触发

#### 论文阅读汇报（每篇 2–4 页）

```text
"讲这篇论文" / "journal club 轮到我"        → 单篇，通常 4 页
"这两篇一起讲"                              → 多篇，自动加一页文献汇总表
"简单过一下这篇"                            → 精简 2 页（slim 模式，缺点只给提示不报错）
```

#### 实验报告（每组 2–4 页）

```text
"这周的实验做个报告"                        → 单组，通常 3 页
"两组实验都要报"                            → 两组，各 2–4 页，自动分区
"把这次的消融也加上"                        → 同一单元补页，仍受 4 页上限约束
```

#### 项目进展汇报（每个项目 2–4 页）

```text
"基金中期检查要过一遍进度"                  → 科研项目，按任务书节点对账
"老师那个横向项目报一下进展"                → 委托项目，按合同里程碑对账
"两个项目一起报"                            → 多单元，自动分区
```

### 每类汇报要讲什么

内容点不是建议，是**检查脚本会逐条核对的清单**。填不出来，说明还没读透。

#### 论文阅读汇报（9 个内容点）

- **文献标题**（`name`）—— 中文名 + 英文原名。
- **出处与等级**（`source`）—— 期刊/会议全称、年份、CCF 等级/中科院分区；**查不到就写「未核实」，不许猜**。
- **作者观点与理论**（`thesis`）—— 一句话说出作者到底主张什么。
- **推理与论证过程**（`argument`）—— 从问题到结论的链条，哪一步是关键跳跃。
- **所解决的问题**（`problem`）—— 之前的方法卡在哪。
- **文章贡献**（`contribution`）—— 相对已有工作新在哪（不是复述摘要）。
- **实验设计**（`experiment`）—— 数据集、基线、指标，整体设计一句话。
- **实验 ↔ 观点对应**（`mapping`）—— **必须用表格**：哪个实验印证哪条观点、证据在第几页。
- **个人启发**（`insight`）—— 对你自己的课题意味着什么（这是导师最想听的）。

多篇论文时，在论文分区页之后先放**一页文献汇总表**（`roles: ["summary_table"]`），列固定为 `文献标题 | 出处 | 发布时间 | 一句话核心内容`，**行数必须等于篇数**。

#### 实验报告（7 个内容点）

- **实验名称**（`name`）—— 一句话说清这是在验证什么。
- **实验目的**（`purpose`）—— 要回答的问题，是可判定的。
- **实验设置**（`setup`）—— 数据、模型、超参、硬件、随机种子。
- **核心发现**（`finding`）—— 给数字与对照，不只给最优那条线。
- **局限**（`limit`）—— 短文本任务、单语料、单种子这类要说清。
- **后续可做**（`next`）—— 每条能验收。
- **结论**（`conclusion`）—— 回到实验目的：回答了什么。

#### 项目进展汇报（4 个内容点）

- **项目名称**（`name`）—— 见下表的写法差异。
- **当前进度**（`progress`）—— 拿什么对账，见下表。
- **当前遇到的问题**（`problem`）—— 卡在哪，卡了多久，谁在等谁。
- **下一步展望与规划**（`plan`）—— 具体到日期或周，标注哪些要老师拍板。

### 支持的项目类型

**这里的「项目」只指有立项或合同的活**，两类，写法不同：

|                | A 科研项目                                         | B 委托 / 外包项目                                    |
| -------------- | -------------------------------------------------- | ---------------------------------------------------- |
| 典型来源       | 国自然/省基金、重点研发子课题、横向课题            | 老师接的企业、事业单位开发或算法委托                 |
| 名称要写全     | 项目类别 + 项目名 + 编号 + 起止年 + 我的角色       | 委托方 + 项目名 + 合同期 + 我的角色                  |
| 进度拿什么对账 | 任务书节点、结题指标（论文/专利/数据集）           | 合同里程碑、交付物（原型/接口/试运行/验收）          |
| 卡点长什么样   | 标注跟不上、算力不够、方法不收敛、合作单位数据未到 | 甲方权限没开、需求变更、验收标准分歧、现场机器跑不动 |

两条硬规矩：

- **「读了几篇文献、写了多少字、commit 多少」不算项目进度**——那是个人学习量，归论文或实验类。
- 委托项目**必须脱敏**（不写合同金额、甲方内部系统名、人员全名），且**不替老师承诺排期**（写「建议顺延一周，待老师与甲方确认」，而不是「我把 M4 改到 12-20」）。

## 数据格式：`deck.json`

### 三级结构

```
deck.json
├── meta / cover / agenda / end      ← 全局
└── parts[]                          ← 种类（paper / experiment / project）
    ├── pages[]                      ← 种类级页面（如文献汇总表）
    └── units[]                      ← 单元（一篇论文 / 一组实验 / 一个项目）
        └── pages[]                  ← 内容页，必须 2–4 页
```

封面、目录、分区页、页码、页脚都是自动生成的，你只写内容页。

### 最小可运行示例（一篇论文 3 页）

```json
{
  "meta": { "title": "组会汇报", "footer": "第 12 周组会" },
  "cover": { "title": "一篇论文：ReAct", "subtitle": "机制与我的启发" },
  "agenda": true,
  "parts": [
    {
      "kind": "paper",
      "title": "论文阅读汇报",
      "subtitle": "本周精读一篇",
      "units": [
        {
          "name": "ReAct：推理与行动的交替",
          "pages": [
            {
              "type": "cards",
              "roles": ["name", "source"],
              "title": "标题与出处",
              "entries": [
                { "label": "标题", "value": "ReAct：推理与行动的交替", "strong": true },
                { "label": "出处", "value": "ICLR 2023（CCF-A）" },
                { "label": "时间", "value": "2022-10" }
              ]
            },
            {
              "type": "image",
              "roles": ["thesis", "problem", "argument"],
              "title": "主张：思考与行动必须交替",
              "bullets": [
                "总观点：只推理不行动，模型会一路自圆其说。",
                { "text": "论证：把观测结果写回上下文，作为下一轮推理的前提", "level": 1 },
                "解决的问题：纯推理拿不到外部事实，纯行动无法复用已有结论。"
              ],
              "image": "figs/f1.png",
              "caption": "图 1　Thought–Act–Observation 循环（原文 p.2 Figure 1）",
              "source": "原文 p.2 Figure 1",
              "evidence": true,
              "takeaway": "关键不是加一句「请先思考」，而是让观测改写推理。"
            },
            {
              "type": "table",
              "roles": ["experiment", "mapping", "contribution", "insight"],
              "title": "实验如何印证观点",
              "columns": ["实验", "印证的观点", "证据位置"],
              "rows": [
                ["HotpotQA 多跳问答", "交替优于纯推理与纯行动", "Table 1"],
                ["消融：去掉观测", "观测是增益来源", "Table 3"]
              ],
              "col_widths": [0.32, 0.44, 0.24],
              "takeaway": "需要多步外部信息时，交替的优势最明显；我的综述可按此设对照。"
            }
          ]
        }
      ]
    }
  ],
  "end": { "title": "谢谢，请老师和同学批评指正" }
}
```

> 三段分别对应：出处 → 观点与论证（配原文框架图）→ 实验如何印证观点 + 我的启发。
> 论文类要讲全 9 个内容点，靠每页的 `roles` 登记，不是靠标题里出现关键词。

### 每页通用字段

| 字段             | 作用                                                     |
| ---------------- | -------------------------------------------------------- |
| `type`           | 版式，见下表；不写默认 `bullets`                         |
| `roles`          | 内容点标签，**检查脚本靠它核对**，一页可登记多个         |
| `title`          | 页标题，写成判断句，≤30 字                               |
| `takeaway`       | 页脚上方结论条，≤45 字，「这一页到底说明什么」           |
| `source`         | 出处，渲染进页脚（`原文 p.5 Table 1`），被追问时能翻回去 |
| `notes`          | 演讲备注，写进备注栏不显示在页面上                       |
| `evidence`       | `true` 标记这是证据页，供检查统计                        |
| `kicker` / `sub` | 标题上方小标签 / 标题下一句补充，一般不写（自动生成）    |

### 六种版式，别自己发明

| `type`      | 用来表达                                     | 关键字段                                                   |
| ----------- | -------------------------------------------- | ---------------------------------------------------------- |
| `bullets`   | 有先后的要点、观点、问题、计划（一级 ≤6 条） | `bullets`（字符串，或 `{text, level, bold}`）              |
| `image`     | 原文/结果图作证据，左图右文                  | `image`（必填）、`caption`、`image_ratio`、`image_side`    |
| `table`     | 对照关系：实验↔观点、指标对比                | `columns`、`rows`、`col_widths`（和为 1）、`highlight_col` |
| `cards`     | 并列事实：标题、出处、目的、设置             | `entries: [{label, value, strong}]`、`cols`                |
| `columns`   | 2–4 栏并列：进度/问题/下一步、局限/后续/结论 | `columns: [{heading, bullets}]`                            |
| `statement` | 一句必须让全场记住的话                       | `text`、`attribution`                                      |

`cover` / `end` / `agenda` 不用手写，自动生成。

### 文本标记

正文里可用 `**加粗**` 和 `__强调色加粗__`（后者给关键词用）。图片路径写相对 `deck.json` 的路径（推荐 `figs/xxx.png`），文件不存在会在生成前就报错（退出码 3），不会生成一半。

### 表格的硬规则（踩过坑的）

- `col_widths` 之和为 1，列宽差距不要超过 2.5 倍；
- 单元格 ≤28 字，超了自动降字号，降到 12pt 还塞不下就打 `[warn] 表格偏密`——此时**精简文字或拆页**，不要加宽表格；
- 别在一格里写 `2022-10 / 2023-05` 这种双值，列窄时会断在斜杠上，很难看。

## 设计取舍：五个坑是怎么被塞进脚本的

### 出了什么问题

第一版跑通样例时，逐页看渲染图，逮到四个「脚本不报错、但投出来难看」的版面问题，外加一个只在 Windows 上出现的导出坑：

1. **文字压到底部结论条**。按字数估算高度、选字号，估小了 5%，正文最后一行就钻进结论条里。样例第 12 页原样如此，`check_deck.py` 也没报——因为两个形状都「没出页面」，只是互相压着。
2. **表格上挤下空**。4 行表按内容算完高度只占半页，剩下半页空着，视觉重心全在页面上半部。往表格里加行不对，去掉行也不对。
3. **句号被挤到下一行**。中文避头尾规则没生效，末行只剩一个「。」——16pt 屏上就是一行孤零零的标点。
4. **分区页和多栏页的强调线撞成「双线」**。栏顶原本画的是强调色短线，左边缘恰好和页标题的强调线重叠，远看像画歪了。
5. 另外还有一个只在 Windows 上出现的：PowerPoint 的 COM 接口会按文件路径复用已打开的文档，**同一路径反复「生成 + 导出」，导出的是旧内容**。第一次遇到会以为是缓存，其实是拿到了上一次的渲染。

### 我们改了什么

**版面重算**（`build_deck.py`）

- 不再按字数估，改用**真实字体度量**（`PIL.ImageFont.getlength`）算每一行宽度，并与 `check_deck.py` 用同一口径——避免「生成时算得下、体检时算溢出」这种自相矛盾。
- 要点块按**可用高度反算**字号与段间距：塞得下就放大到 22pt，塞不下逐档降，最低 14pt。
- 表格行数少时把行高撑开、整体略微垂直居中，不再「表格在上半页、下半页空一片」。
- 段落加 `hangingPunc="1"` + `lang="zh-CN"`，让 PowerPoint 按中文避头尾规则断行，孤标点不再出现。
- 多栏页的栏顶改**细灰线**，与页标题的强调线区分开，不再撞成双线。

**提前预警**（`build_deck.py`）

- `widow_hits()` 在生成前预测每一段的断行位置，末行只剩一两个字就打 `[hint]`，让你先改措辞，而不是等导出图才发现。
- 内容占不到版面 45% 时打 `[warn] 内容偏少`，提示补一条具体结果或与相邻页合并。

**导出可靠性**（`render_deck.ps1`）

- 导出前先复制成唯一临时文件名再交给 PowerPoint，绕开上面第 5 条那个「复用旧文档」的坑。
- `.ps1` 含中文必须存成 UTF-8 with BOM，否则 PowerShell 5.1 会按 GBK 解析，中文路径直接乱码报错。

### 为什么重要

这些问题都不是「AI 生成错了」，而是**估算法与真实排版之间的缝**：字数估算 vs 真实字宽、计算高度 vs 实际行高、期望断行 vs 引擎避头尾。缝很小，但一定会在某一页裂开。

所以修法不是「这次调一下字号」，而是把这些缝变成脚本里的硬逻辑——下次换内容、换字体、换页数，同一类问题不会再出现。这也是为什么这个技能坚持「六种版式 + 固定设计系统」：**可预测的版式才能被自动检查**，自由画布只能靠人一页页盯。

## 报错对照表

| 看到什么                   | 意思                            | 怎么办                                          |
| -------------------------- | ------------------------------- | ----------------------------------------------- |
| 退出码 **5**，单元页数越界 | 某篇/某组/某项目不是 2–4 页     | 合并或拆分内容页                                |
| 退出码 **3**，图片不存在   | `image` 路径写错或图还没裁      | 先按第六节裁图，再改路径                        |
| 退出码 **2**，未知版式     | `type` 用了表里没有的值         | 只能用六种版式之一                              |
| `[FAIL] 缺内容点：…`       | 该登记的内容点没登记            | 在对应页的 `roles` 里加上，或确实没内容就补内容 |
| `[warn] 表格偏密`          | 行太多/字太多，最小字号也塞不下 | 精简单元格文字或拆成两页                        |
| `[hint] 末行只剩一两个字`  | 孤字，投出来难看                | 改写措辞，增减几个字让断行位置变掉              |
| `[warn] 内容偏少`          | 一页只占版面不到一半            | 补一条具体结果，或与相邻页合并                  |
| `[FAIL] 插图 dpi 不足`     | 图是从网页/低分辨率截图来的     | 用 300–400dpi 重新渲染原文页面再裁              |

## 六个实用技巧

1. **页数由内容决定，不由图决定**。一页塞两张图必然压字；宁可按 4 页讲。
2. **一级要点超过 6 条就拆页**，正文超过 260 字也拆。听众读不完的时候，就不听了。
3. **`takeaway` 是最值钱的字段**。每页写一句「所以呢」，被追问时你回的就是这句。
4. **`source` 写在页脚不是形式**。导师问「这个数字哪来的」，你能直接说「原文第 5 页表 1」。
5. **同一单元内页脚自动带 `论文阅读汇报 · 2/3`**，所以不用手写 `kicker`；写了反而会覆盖掉正确的计数。
6. **改内容只改 deck.json 再重新生成**，不要在 PowerPoint 里手动改——下次重新生成会把你的手改覆盖掉。

## 常见问题

**Q：一定要会 Python 吗？**
不用。你只说「做一份组会汇报 PPT，讲这两篇论文」，AI 会写 deck.json 并跑那些命令。只有自己动手改内容时，才需要动 JSON——而 JSON 只是「大括号套大括号」，照抄样例改文字即可。

**Q：图片必须自己截吗？**
论文里的图必须来自原文，不能自己画。用 `crop_figure.py` 三步：整页渲染 → `--propose` 看候选框 → `--bbox` 裁切并自动判定完整性。

**Q：没有原文 PDF，只有摘要网页？**
那就没有原文图可截。此时在单元里写 `"no_evidence_reason": "只有摘要，无原文图表"`，改用文字证据——**绝不自己画一张图冒充原文**。

**Q：为什么生成完还要人看图？**
脚本能算出「文字框有没有溢出」，算不出「这页看着别扭」。排版问题九成出在视觉上，所以最后一关只能靠眼睛。

**Q：换台电脑还能用吗？**
能，但要注意两点：中文字体（Windows 用微软雅黑，macOS 会自动找 PingFang SC）；目检用的 `render_deck.ps1` 依赖 PowerPoint，没装就得手动打开逐页看，并在交付时说明「未做渲染目检」。

**Q：能直接改生成的 pptx 吗？**
能，但改完就「脱轨」了：之后再从 deck.json 重新生成，手改会被覆盖。所以改内容回到 deck.json，PowerPoint 里只做最后的微调并另存。
